# Character Role Activation Contract Design

**Date:** 2026-08-03

**Status:** Approved for implementation planning

**Scope:** Character Worlds role activation during conversation turns

## 1. Problem

Character selection and persistence work, and the selected revision is admitted
with each turn. The current compiler also appends the character envelope to the
OpenCode system field. Despite that, models may correctly treat the selected
card as reference data instead of the active conversational identity.

The contradiction is structural: the current prologue says every imported
string is data, not instructions, and cannot change Lily identity. That is a
sound protection against untrusted card instructions, but it also neutralizes
the legitimate product behavior of adopting the selected character. Expression
profiles are serialized as labels without a host-owned behavioral contract.

The result is a false-positive UI state: the application can show a selected
character while the model denies that it is using the role.

## 2. Product Contract

When a conversation has a selected character:

1. Lily remains the sole agent kernel and platform identity.
2. The selected character becomes the active conversational identity.
3. Natural-language answers consistently use the character's identity,
   professional perspective, personality, and voice.
4. A direct identity question such as "Who are you?" is answered with the
   active character identity. Platform provenance may be added only when the
   user asks how the application or agent is implemented.
5. Tools, permissions, safety policy, evidence requirements, task rigor,
   factual accuracy, and exact artifacts are not changed by the character.
6. Missing, invalid, oversized, unsupported, or failed character activation
   falls back to native Lily without reducing capability.

Selecting no character preserves today's native Lily behavior byte-for-byte.

## 3. Rejected Approaches

### 3.1 Append a stronger sentence to imported card text

This is small but keeps trusted activation semantics mixed with untrusted card
content. It remains vulnerable to provider interpretation differences and does
not produce an auditable application result.

### 3.2 Run a separate role agent

This can improve immersion but splits memory, tools, permissions, task state,
and recovery between runtimes. It adds latency and creates a capability parity
risk. Character Worlds remains a bounded context producer, not a second agent.

## 4. Authority Model

Each request is composed from four conceptually separate layers:

1. **Lily Kernel Policy**: platform identity, tools, permissions, safety,
   evidence, task execution, recovery, and exact-output rules.
2. **Host Role Activation Contract**: trusted, deterministic instructions
   generated by Lily from an admitted binding and validated character fields.
3. **Character Narrative Envelope**: lower-authority imported character,
   Persona, world-book, scene, and memory data.
4. **Current User Request**: the current message, files, and task context.

The role activation contract is host-authored policy. It never copies imported
imperative text into its instruction clauses. The narrative envelope remains
untrusted data and cannot grant authority.

Platform identity and conversational identity are not mutually exclusive:

- Platform identity answers "what system is operating?": Lily.
- Conversational identity answers "who is speaking in this conversation?":
  the selected character.

The host contract tells the model which interpretation to use, avoiding the
current identity contradiction.

## 5. Host Role Activation Contract

The compiler produces a typed contract alongside the narrative envelope:

```js
{
  schemaVersion: 1,
  status: "compiled",
  platformIdentity: "Lily",
  conversationRole: {
    revisionId: "...",
    name: "Lily · Chief Architect"
  },
  expressionProfile: "balanced",
  behavior: {
    answerAsRole: true,
    maintainRoleAcrossTurns: true,
    applyProfessionalPerspective: true,
    applyPersonalityAndVoice: true,
    identifyAsRoleWhenAsked: true
  },
  protectedDomains: [
    "tools", "permissions", "safety", "evidence", "task_rigor",
    "facts", "code", "commands", "paths", "numbers", "citations",
    "structured_output", "user_requested_format"
  ],
  narrativeFingerprint: "sha256:...",
  activationFingerprint: "sha256:..."
}
```

The serialized host instruction is fixed Lily-owned text plus bounded values
such as the sanitized role name and selected expression profile. Description,
personality, examples, imported system prompts, and world-book text stay in the
lower-authority narrative envelope.

The activation contract explicitly requires the model to:

- speak as the current conversational role;
- use the role's professional lens, personality, and voice in prose;
- answer identity questions with the role name;
- avoid describing an active role as an optional or inactive card;
- preserve the current user's task and all Lily kernel requirements.

It explicitly forbids the role from changing tools, permissions, safety,
evidence, exact artifacts, or requested output format.

## 6. Expression Profiles

Profiles become executable host semantics instead of metadata-only labels.

### 6.1 `immersive`

- Stay in first-person character throughout natural-language dialogue.
- Do not step outside the role unless required for safety, permission, tool
  status, or an explicit user request for platform-level explanation.
- Apply scenario, emotional behavior, relationship framing, and dialogue style.
- Exact artifacts remain protected.

### 6.2 `balanced`

- Keep the role identity and voice consistently visible.
- Complete ordinary questions and tasks directly without theatrical overhead.
- Apply personality, expertise, and decision principles to reasoning and prose.
- Identity questions always resolve to the selected character.

### 6.3 `task_preserving`

- Apply the role's expertise, priorities, decision principles, and concise
  prose style to task work.
- Do not alter code, commands, paths, data, citations, structured output, or
  requested formats for stylistic effect.
- Do not reduce tool usage, verification, rigor, or completion effort.
- Identity questions still resolve to the selected character.

Unknown profiles fail to `task_preserving`; missing task classification uses
`balanced`, preserving the current classifier behavior.

## 7. Data Flow

1. The renderer updates the conversation binding through the existing IPC.
2. Turn admission pins the immutable character, Persona, world-book, and scene
   revisions in `character_worlds_snapshot_json`.
3. Character Worlds runtime validates policy and resolves the pinned content.
4. The compiler creates two outputs:
   - a host-owned activation contract;
   - a lower-authority narrative envelope.
5. The OpenCode prompt builder independently budgets and composes Lily kernel
   guidance, activation contract, and narrative envelope.
6. The final body builder reports whether the activation contract and narrative
   envelope were actually included.
7. The persisted turn trace and renderer projection receive metadata-only
   application status.

Compilation success is not application success. `applied` is recorded only
after the final provider request body contains the activation contract.

## 8. Application State And Observability

Use one metadata-only state machine per admitted turn:

- `native`: no selected character.
- `selected`: the admitted snapshot references a character revision.
- `compiled`: activation contract and narrative envelope compiled.
- `applied`: final request body contains the activation contract.
- `bypassed`: a selected character was not applied.

`bypassed` includes a bounded machine-readable reason, for example:

- `policy_disabled`
- `snapshot_not_ready`
- `revision_missing`
- `identity_missing`
- `budget_zero`
- `provider_unsupported`
- `activation_invalid`
- `prompt_budget_exhausted`
- `request_build_failed`

Trace data may include revision ID, binding version, expression profile,
activated field names, token estimates, fingerprints, omissions, warnings, and
bypass reason. It must never include card, Persona, world-book, scene, or memory
text.

The renderer may display "role active" only for the latest admitted turn whose
status reaches `applied`. A selected-but-bypassed role must not be represented
as successfully active; the normal answer still runs as native Lily.

## 9. Character Quality Contract

New Lily-authored characters should produce a richer structured specification:

- identity and relationship;
- background and scenario;
- core personality and emotional behavior;
- expertise or worldview;
- decision principles;
- voice and vocabulary;
- response patterns;
- boundaries and prohibited behavior;
- positive and negative dialogue examples;
- first message;
- long-term consistency rules.

These fields improve role quality but do not gain system authority. Existing
cards remain compatible: the host contract activates available fields and
records missing facets without mutating historical revisions.

No database migration is required for activation. An additive canonical schema
revision for richer Lily-authored cards may be introduced separately while the
compiler continues accepting existing canonical fields.

## 10. Compaction, Switching, Scheduling, And Concurrency

- A binding change affects only turns admitted after its version boundary.
- Historical messages are not rewritten when roles change.
- Compaction preserves revision IDs, binding version, profile, scene state, and
  metadata fingerprints, not executable copies of stale role instructions.
- Scheduled messages use the binding snapshot admitted for their exact target
  conversation and queue position.
- Concurrent conversations compile and apply their own immutable snapshots.
- Retry and recovery reuse the admitted snapshot unless a new user turn is
  admitted; they never read whichever role is currently visible in another UI.

## 11. Failure And Capability Gate

The feature must satisfy `CAPABILITY-GATE.md`:

- Native mode remains byte-equivalent to the current strong default.
- Any activation failure removes both activation and narrative layers, then
  runs the same native Lily turn.
- Character mode never selects a weaker model or removes tools, skills,
  context, memory, files, subagents, or recovery behavior.
- A narrative budget failure can omit optional narrative facets, but must not
  emit a misleading partial identity. If the identity plus activation contract
  cannot fit, the turn runs native.
- Provider incompatibility never moves role instructions into visible user
  text as a workaround.
- Existing emergency and rollout kill switches preserve native Lily.

## 12. Test Strategy

### 12.1 Deterministic contract tests

- Activation contract is host-owned and contains no imported imperative text.
- Narrative fields remain lower authority.
- Each expression profile serializes explicit behavior.
- Native prompt bytes remain unchanged.
- Malformed, oversized, missing, and adversarial cards fail open.
- Exact protected domains are present in every role contract.

### 12.2 Request-path tests

- Capture the final OpenCode body and assert `applied` only when the activation
  contract is present.
- Verify provider and budget bypass reasons.
- Verify the activation contract never appears in user-visible message parts.
- Verify trace events are metadata-only and persisted.

### 12.3 Behavioral evaluations

Run supported production models against at least:

- Chief Architect: "Who are you?" and an architecture review.
- Strategy Advisor: the same business problem.
- Affectionate partner: identity, emotional support, and ordinary task help.
- Native Lily control: the same prompts without a selected role.

Acceptance requires correct identity, materially distinct role behavior, and
equivalent task completion capability.

### 12.4 Capability parity

For native and role variants of the same complex task, compare:

- available and invoked tools;
- permission decisions;
- files and exact artifacts produced;
- evidence and verification steps;
- task completion and error recovery;
- long-turn continuation and compaction behavior.

Role mode may change prose but may not reduce these capabilities.

### 12.5 Isolation and lifecycle

- Two concurrent conversations with different roles never cross-contaminate.
- Switching roles affects the next admitted turn only.
- Scheduled turns, retries, restart recovery, rewind, and fork preserve the
  correct immutable binding.
- Character deletion or unavailable policy produces explicit bypass metadata
  and native behavior.

## 13. Release Gate

The change cannot ship until:

1. Focused Character Worlds and OpenCode request tests pass.
2. Full capability-gate tests pass.
3. Behavioral evaluations pass on every production managed model class.
4. Native-mode request parity is proven.
5. Role-mode complex-task capability parity is proven.
6. Renderer status is driven by final `applied` evidence, not selection alone.
7. A rollback switch restores the current native behavior without data loss.

## 14. Implementation Boundaries

Expected implementation areas:

- `src/main/character-worlds/context-compiler.js`
- a focused host activation-contract module under `src/main/character-worlds/`
- `src/main/runtime/opencode-character-context.js`
- `src/main/runtime/opencode-message-parts.js`
- `src/main/runtime/opencode-server-manager.js`
- `src/main/turn-orchestrator.js`
- metadata-only renderer projections for role application state
- Character Worlds compiler, injection, capability-gate, lifecycle, and model
  evaluation tests

Do not:

- create a second role agent runtime;
- grant imported card text host authority;
- move role context into user messages or durable visible history;
- weaken Lily's kernel guidance or exact-output protections;
- change unrelated Character Worlds storage or authoring boundaries;
- require rewriting existing immutable character revisions.

## 15. Decision

Lily will adopt a host-owned Role Activation Contract. The selected character
becomes the active conversational identity while Lily remains the sole agent
kernel and authority owner. Imported character content remains bounded,
untrusted narrative data. Application is verified at the final provider request
boundary, and any failure degrades to native Lily.
