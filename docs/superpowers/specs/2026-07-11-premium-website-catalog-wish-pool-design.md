# Lily Workbench 高端官网、应用技能目录与许愿池设计

日期：2026-07-11
状态：已完成交互设计确认，待实施计划

## 目标

把当前偏概念演示的官网升级成可信、成熟、面向个人用户下载与购买的产品入口，同时公开展示 Lily 已发布的应用和技能，并建立“用户提出真实工作需求 → 团队审核与合并 → 公开进度 → 上线后关联应用或技能”的许愿池闭环。

本轮第一转化目标是个人用户下载和购买。企业咨询保留为次要入口，不再主导首页叙事。

## 用户与核心痛点

目标用户是需要处理文档、表格、网页、截图和长期项目资料的个人知识工作者。他们不一定熟悉 AI 工具，也不愿学习复杂提示词。

官网必须直接回应三个痛点：

1. 工作资料散落在多个文件、网页和聊天记录里。
2. 每次使用普通 AI 都要重新解释背景和进度。
3. 普通 AI 往往只给建议，用户仍要自己把建议加工成可交付成果。

核心价值表达为：Lily 从用户选择的真实工作区开始，理解上下文、保留任务连续性，并把工作推进到可使用的结果。

## 已批准的产品与视觉方向

采用“亲和型精品效率工具”方向：明亮、克制、低门槛，像成熟的消费级桌面产品，而不是技术概念页。

### 视觉系统

- 主色：矿物蓝 `#586CE8`，仅用于关键动作、状态和少量品牌强调。
- 标题色：深墨色 `#121827`。
- 背景：珍珠白 `#F6F8FD` 和纯白表面。
- 辅助色：浅薰衣草 `#DCE3FF`；成功状态使用 `#35A47A`。
- 字体：中文优先使用系统字体，英文使用现有 Geist/Inter 回退栈，不新增远程字体依赖。
- 大标题收紧字距，正文保持舒适行高和有限阅读宽度。
- 使用真实 Lily Workbench 客户端画面作为主视觉；画面中的项目资料必须脱敏或使用可信示例数据。
- 删除抽象 AI 大脑、荧光网格、无限漂浮、扫光、旋转和同质图标卡片海洋。
- 动效仅用于一次性入场、按钮状态和幅度小于 12px 的首屏产品视差。
- 完整支持 `prefers-reduced-motion`，禁用非必要动画。

高级感来自真实产品、清晰比例、可信文案和克制，而不是视觉特效。

## 范围

### 包含

- 重构官网首页、顶部导航、页脚和公开页面元信息。
- 新增公开应用目录页 `/apps`。
- 新增公开技能目录页 `/skills`。
- 新增许愿池页 `/wishes`。
- 首页展示来自公开目录的少量精选应用和技能。
- 新增许愿池服务端数据模型、公开接口、登录用户操作接口和管理接口。
- 新增许愿池管理后台页面。
- 中文、英文、阿拉伯文文案和 RTL 验证。
- 桌面端和移动端响应式实现。

### 不包含

- 不重做账号、订单、支付、权益和管理后台的整体视觉。
- 不改变应用和技能的发布、签名、授权或客户端下载协议。
- 不新增许愿池评论、私信、用户主页或公开提交即展示。
- 第一版不展示未经真实数据支持的虚假票数、用户数、Logo 墙或客户证言。
- 不新增与官网目标无关的桌面客户端能力。

## 官网信息架构

顶部导航为：产品、应用、技能、许愿池、价格。右侧保留登录和“免费下载”。移动端使用可访问的折叠菜单。

### 首页

首页按一次完整购买说服组织：

1. **首屏**
   - 主标题：“你的项目，终于有人记得。”
   - 说明 Lily 把文件、网页和对话放进同一工作区，理解上下文并推进复杂工作。
   - 主按钮：“免费下载”，继续使用现有 `/download` 路径。
   - 次按钮：“看看它如何工作”，滚动到 `#product-demo` 产品演示区。本轮没有真实视频资产，因此不展示“90 秒演示”或空视频链接。
   - 明确支持的平台，以发布接口实际可下载的平台为准，不硬编码不存在的安装包。
   - 使用真实客户端截图，产品画面承担首屏主要视觉重量。

2. **可信能力摘要**
   - 项目上下文、跨格式理解、持续记忆、真实交付。
   - 不使用未经验证的数量指标。

3. **痛点到结果**
   - 把现场交给 Lily。
   - Lily 先理解上下文。
   - 用户得到可使用结果。

4. **真实工作场景**
   - 项目研究。
   - 文档工作。
   - 长期项目。
   - 问题排查。
   - 每个场景展示“输入材料 → Lily 的判断 → 最终交付”，避免纯功能卡片。

5. **精选应用**
   - 从 `/api/apps/catalog` 读取匿名用户可见、已启用且 `featured` 的应用。
   - 最多显示三项；不伪造目录内容。
   - 链接到 `/apps`，应用使用动作引导至 Lily 下载或客户端内使用，不绕过现有授权下载门槛。

6. **精选技能**
   - 从 `/api/skills/registry` 读取 `displayInCatalog !== false` 且 `featured` 的技能。
   - 最多显示六项，使用本地化名称和描述。
   - 链接到 `/skills`。

7. **安全与可信边界**
   - 用户主动选择工作区。
   - 不无边界扫描整台电脑。
   - 不同任务保持独立上下文。
   - 操作过程和结果在对话中可见。
   - 隐私文案必须与真实云模型、网关和本地存储行为一致，不写“完全离线”或“文件永不发送”等过度承诺。

8. **许愿池入口**
   - 展示少量已计划、实现中或已上线愿望。
   - 主链接进入 `/wishes`。

9. **最终下载 CTA**
   - 再次强调从一个真实文件夹开始。
   - 企业咨询放到页脚或次级入口。

## 应用目录

`/apps` 使用现有 `/api/apps/catalog`，不创建第二套应用数据源。

- 匿名访问按现有服务端规则只能看到 `free` 计划可见的应用。
- 官网不得传伪造设备 ID 或绕过 `minPlan` 可见性。
- 页面支持分类筛选、精选标记和应用类型展示。
- 卡片显示名称、摘要、发布者、类型、分类、版本和实际可见的计划信息。
- 应用详情使用独立路由 `/apps/[id]`，便于分享、SEO 和从已上线愿望直接关联。
- 官网不直接解析或安装应用包；实际获取仍遵守现有签名设备和授权下载接口。
- 目录接口失败时展示明确的暂时不可用状态，同时保留下载 Lily 的入口；首页则直接省略精选目录区，不阻塞主体内容。

## 技能目录

`/skills` 使用现有 `/api/skills/registry`，不读取客户端本地技能目录，也不复制 registry JSON。

- 仅展示 `displayInCatalog !== false` 的条目。
- 使用 `name_i18n`、`description_i18n` 和分类本地化字段，缺失时回退到基础字段。
- 支持分类筛选、精选标记和风险层级的用户友好解释。
- 不把底层 ZIP、SHA256、能力契约或安装协议作为首要营销信息。
- 技能操作引导用户下载或打开 Lily，不在浏览器中执行技能。
- 接口失败时显示可恢复空状态，首页主体继续正常渲染。

## 许愿池产品设计

公开名称保留“许愿池”，副标题为“需求共创计划”。页面核心文案为：“一起决定，Lily 下一步学会什么。”

### 交互原则

- 浏览公开愿望不要求登录。
- 提交愿望和点击“我也需要”必须使用现有 Lily Web 账号登录。
- 页面先展示公开愿望和进度，提交表单是次级入口。
- 用户提交的是工作问题，不要求用户替产品团队设计功能。
- 表单字段为：想完成什么、当前最卡在哪里、理想结果是什么。
- 提交前服务端返回可能相似的公开愿望；用户可选择支持已有愿望或继续提交。
- 新愿望默认私有且待审核，绝不直接进入公开列表。
- 管理员可以修改公开标题和描述、合并重复愿望、设置分类、发布、更新状态和关联最终应用或技能。
- “已上线”状态必须至少关联一个已启用应用或可展示技能，避免空洞完成状态。
- 第一版没有评论、私信和用户公开主页。
- 第一版公开 UI 不显示精确支持数；真实支持数用于排序和后台判断，避免低样本数字削弱可信度。

### 状态模型

内部状态：

- `pending`：已提交，仅提交者和管理员可见。
- `reviewing`：管理员正在评估，仍不公开。
- `published`：已审核并公开，但尚未承诺排期。
- `planned`：已纳入计划。
- `building`：正在实现。
- `shipped`：已上线，必须关联应用或技能。
- `declined`：不采用，仅提交者和管理员可见，带内部或用户可见说明。
- `merged`：合并到另一个愿望，支持关系迁移到目标愿望。

公开列表只返回 `published`、`planned`、`building` 和 `shipped`。

### 数据模型

新增 `feature_wishes`：

- `id`：公开安全 ID。
- `submitter_user_id`：提交用户，引用现有用户表。
- `title`：用户原始标题。
- `problem`：当前阻塞。
- `desired_outcome`：理想结果。
- `public_title`、`public_summary`：管理员审核后的中文公开文案。
- `public_title_i18n`、`public_summary_i18n`：英文和阿拉伯文公开文案映射。
- `category`：受控分类。
- `status`：上述状态枚举。
- `public_update`、`public_update_i18n`：公开进展说明及其英文、阿拉伯文映射。
- `submitter_status_note`：只向提交者展示的审核、拒绝或合并说明。
- `merged_into_id`：合并目标。
- `linked_app_ids`、`linked_skill_ids`：已上线成果关联。
- `published_at`、`created_at`、`updated_at`。

新增 `feature_wish_supporters`：

- `wish_id`。
- `user_id`。
- `created_at`。
- `(wish_id, user_id)` 唯一约束，保证每个账号只能支持一次。

第一版不增加公开附件。这样避免把用户工作资料误公开，也保持实现范围可控。后续如确需附件，必须使用私有对象存储并由管理员单独审核。

### 接口

公开接口：

- `GET /api/wishes`：仅返回公开状态，支持状态、分类和排序参数。
- `GET /api/wishes/:id`：仅返回公开愿望或当前用户自己的非公开愿望。
- 响应永不包含用户 ID、手机号、邮箱、IP、User-Agent、内部备注或原始私密字段。

登录用户接口：

- `POST /api/wishes/similar`：在提交前查找相似的公开愿望；第一版使用确定性的标题与关键词匹配，不引入模型调用。
- `POST /api/wishes`：创建 `pending` 愿望。
- `POST /api/wishes/:id/support`：幂等支持公开愿望。
- `DELETE /api/wishes/:id/support`：撤销支持。
- `GET /api/account/wishes`：查看自己的提交、状态和合并去向。

管理接口：

- `GET /api/admin/wishes`：按状态、分类和时间筛选。
- `PATCH /api/admin/wishes/:id`：审核公开文案、分类、状态、进展和成果关联。
- `POST /api/admin/wishes/:id/merge`：事务内迁移支持关系并标记源愿望为 `merged`。

账号认证复用现有 `lily_user_session` 和服务端 Web session 验证。实现时应抽取或复用共享的 session resolver，不复制一份宽松认证逻辑。

### 管理后台

新增 `/admin/wishes`，使用现有 AdminShell 和表格/表单风格，不重做后台视觉。

管理员可以：

- 查看待审核、公开、计划中、实现中、已上线、拒绝和合并记录。
- 查看真实支持数和相似候选。
- 编辑公开文案并发布。
- 合并重复愿望。
- 更新公开进展。
- 从现有应用和技能目录中选择成果关联。
- 只有满足关联约束时才能设为 `shipped`。

## 数据流

### 目录展示

1. Next.js 服务端页面请求现有公开应用或技能接口。
2. 服务端按既有可见性和目录规则返回内容。
3. 官网只做本地化、筛选和展示，不改变授权语义。
4. 接口异常时页面渲染明确空状态，首页主转化不受影响。

### 愿望提交

1. 用户登录 Lily Web 账号。
2. 用户填写工作问题、阻塞和理想结果。
3. 页面先调用相似愿望接口。
4. 用户支持已有愿望，或确认创建新的 `pending` 愿望。
5. 管理员审核、去重并决定是否公开。
6. 公开愿望进入热度排序和状态更新流程。
7. 实现完成后管理员关联应用或技能并标记 `shipped`。

## 组件边界

首页不继续堆在单个超长文件中，但也不为每个小块创建抽象。实现使用以下边界：

- `HomeHero`：首屏文案、下载 CTA、真实产品画面。
- `HomeWorkflows`：痛点到结果与真实场景。
- `FeaturedCatalog`：应用和技能精选，接受已经规范化的数据。
- `HomeTrust`：可信边界。
- `WishPoolPreview`：少量公开愿望和入口。
- `CatalogCard`：应用/技能目录共享的表面样式，不共享业务字段转换。
- `WishBoard`、`WishSubmitForm`、`WishSupportButton`：愿望浏览、提交和登录后支持。

目录数据规范化放在 `web/lib` 的纯函数中，便于测试多语言回退、显示过滤和接口失败行为。服务端状态转换和公开序列化放在独立 wish service 中，路由不直接拼装敏感字段。

## 失败处理与能力门禁

- 应用或技能接口失败：官网仍展示完整首页和下载 CTA，目录区显示空状态或在首页省略，不能让整页报错。
- 真实产品图加载失败：保留文本、CTA 和稳定占位背景，不出现破图图标。
- 愿望列表失败：显示重试入口，不把空数组伪装成“暂时没有愿望”。
- 愿望提交失败：保留用户输入，显示明确错误与重试动作。
- 未登录支持或提交：跳转登录并保留返回地址，不静默失败。
- 重复支持：接口幂等返回当前已支持状态。
- 重复愿望合并：在事务内迁移支持关系；失败时源愿望和支持数据保持原状。
- `shipped` 缺少有效成果关联：服务端拒绝状态更新。
- 未审核或私密愿望：任何公开接口都不得返回。
- 所有新增能力失败时，现有下载、账户、支付、应用目录和技能同步路径保持原行为。

## 安全与滥用控制

- 提交与支持要求有效 Web session。
- 对创建愿望、相似查询和支持操作分别限流。
- 对标题和正文执行长度、Unicode 和内容类型校验；输出统一转义，不渲染用户 HTML。
- 管理员公开前必须确认公开文案不含联系方式、公司机密或附件内容。
- 公开 API 使用显式 allow-list serializer，禁止 `selectAll()` 后直接返回数据库行。
- 合并和状态变更进入现有管理员审计日志。
- 用户只能查看自己的非公开愿望，不能按可猜测 ID 读取他人提交。

## 多语言、RTL 与内容策略

- 首页、目录页、许愿池和新增后台导航补齐中文、英文和阿拉伯文。
- 应用优先使用现有基础字段；应用表尚无 i18n 字段时，第一版显示服务端内容，不伪造翻译。后续是否补应用 i18n 属于单独能力变更。
- 技能使用 registry 已提供的 i18n 字段。
- 用户愿望不自动机器翻译；公开文案由管理员按主要站点语言编辑。公开 serializer 按当前 locale 读取 i18n 字段，缺失时回退中文并在卡片上标记原文语言。
- 阿拉伯文验证 RTL 导航、筛选、状态标签、卡片和表单布局。

## SEO、性能与可访问性

- 更新首页 title、description、Open Graph 基础元信息。
- 为 `/apps`、`/skills`、`/wishes` 提供独立元信息和规范 URL。
- 服务端首屏渲染核心文案；目录请求设置有界超时和安全回退。
- 产品截图使用 WebP/AVIF 和响应式尺寸，限制首屏资源体积。
- 所有交互具备键盘焦点、语义标签、可读错误和足够对比度。
- 移动端不出现横向滚动；按钮触控尺寸至少 44px。
- 不依赖动画传递唯一信息，并支持减少动态效果。

## 测试与验收

### 自动化

- 官网生产构建通过。

- 许愿认证测试：匿名可读公开列表，匿名不能提交或支持。
- 支持幂等与唯一约束测试。
- 合并事务测试：支持迁移、重复去重、失败回滚。
- 用户隔离测试：不能读取他人的非公开愿望。
- 管理接口测试：审核、发布、状态更新、成果关联和审计记录。
- 能力门禁测试：应用/技能/愿望接口异常时首页和下载路径仍可用。

### 浏览器验收

- 桌面宽屏、笔记本、平板和常见手机宽度截图。
- 中文、英文、阿拉伯文和 RTL。
- 顶部导航、移动菜单、登录返回、下载 CTA。
- 应用和技能筛选、空状态和接口错误状态。
- 愿望提交、相似提示、支持/撤销、管理员审核、合并和上线关联。
- 键盘导航、焦点可见性、表单错误、减少动态效果。

## 成功标准
