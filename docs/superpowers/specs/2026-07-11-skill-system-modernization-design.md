# Lily Workbench 技能系统现代化设计

日期：2026-07-11
状态：已完成设计确认，待实施计划

## 目标

系统性修复当前技能目录、意图路由、运行时依赖、权限声明、注册表缓存和同步脚本之间的漂移，使 Lily 能稳定理解并完成页面视觉设计、前端应用创建、浏览器验证以及其他已声明的技能任务。

本轮不是恢复一个旧的“frontend-design”技能，而是把现有一方技能整理为清晰、可测试、可执行的能力链，同时移除不可达和过时内容。

## 已确认决策

采用“完整迁移、保持能力分层”方案：

- `lily-app-builder` 负责页面和应用的创建与运行。
- `lily-ui-quality` 负责视觉、交互、响应式、可访问性和本地化质量判断。
- `lily-browser-qa` 负责真实浏览器验证和证据采集。
- `lily-code-repair` 负责失败后的诊断与修复闭环。
- `lily-coding-core` 只承担通用工程纪律和上述技能的编排，不复制详细 UI 规范。
- 不恢复过时的 `anthropics-frontend-design`，也不保留失效兼容别名。
- 从生产 `resources/skills-catalog` 删除 8 个未注册孤儿目录，只保留 Git 历史和上游来源，不继续随应用打包。

## 成功标准

1. 常见中英文页面设计、落地页、登录页、美化和重设计请求能进入正确技能链。
2. UI 创建、质量审查和浏览器验证各自职责清楚，且能在需要时组合。
3. `lily-browser-qa` 能发现或安装正确的 Web Automation 运行包，并获得真实浏览器工具；运行包不可用时明确失败并给出恢复路径，不静默伪造验证。
4. 所有一方操作型技能都有准确的 manifest、权限、子进程和运行包声明。
5. 技能正文变化能使本地缓存失效，不再依赖人工修改 `updatedAt` 或碰巧提升版本号。
6. 技能同步默认安全，不会用外部上游目录覆盖 Lily 一方注册信息。
7. 生产 catalog 不包含未注册、不可达或已过时技能。
8. 自动化测试覆盖此前通过测试但实际失效的路径。
9. 现有强能力默认保持可用；新依赖不可用时遵守 `CAPABILITY-GATE.md` 的 fail-open 和可恢复原则。

## 能力架构

### 页面和应用创建

`lily-app-builder` 接收明确的创建意图，包括页面、组件、网站、落地页、登录页、仪表盘和小型 Web 应用。它负责读取现有项目约束、生成或修改代码、启动开发服务，并把长时运行服务交给 `lily_process_jobs` 管理。

创建任务默认同时注入 `lily-ui-quality`，用于在实现前建立视觉和交互约束；需要实际渲染或用户明确要求检查时再注入 `lily-browser-qa`。浏览器验证发现问题后使用 `lily-code-repair`，但修复循环按“是否继续产生进展”终止，而不是固定只修一轮。

### UI 质量

`lily-ui-quality` 增加两个明确模式：

- 创建模式：建立信息层级、视觉方向、排版、颜色、间距、组件状态、响应式和动效规则，并指导实现。
- 审查模式：基于页面和证据识别问题，按影响排序并给出可执行修改。

两种模式共同覆盖：键盘操作、可见焦点、语义和标签、颜色对比度、200% 缩放、减少动效、触控目标、错误和加载状态、长文本、空状态、内容压力、深浅主题、移动端、RTL 以及中文/英文/阿拉伯文布局。

UI 质量技能负责判断标准，不宣称已经执行浏览器检查。需要运行证据时必须交给 `lily-browser-qa`。

### 浏览器验证

`lily-browser-qa` 使用 Web Automation 运行包中的 Playwright 能力，执行明确视口下的页面打开、交互、断言、控制台检查和截图。验证结果必须说明 URL、视口、执行步骤、实际结果和未覆盖项。

运行包预检把 `lily-browser-qa`、需要真实页面证据的 `lily-app-builder` 和相关 Web 学习技能映射到 `web-automation`。MCP 配置优先解析已安装运行包的实际路径，再回退到基础运行时或可用的系统浏览器。若都不可用，返回结构化可恢复错误，并引导用户安装运行包；不得把工具不可用描述成 QA 已通过。

### 修复闭环

推荐链路为：

`lily-app-builder` → `lily-ui-quality` → `lily-browser-qa` → `lily-code-repair` → 重新验证。

技能编排不要求每个请求无条件执行完整链路：纯设计建议不启动服务，纯代码创建不伪造浏览器验证，用户明确要求审查现有页面时可从 UI 质量和浏览器 QA 开始。

## 意图路由设计

### 规则更新

删除所有指向不存在短 ID `frontend-design` 的规则，统一使用正式技能 ID。页面创建意图覆盖但不限于：

- 中文：设计页面、制作页面、美化、重新设计、改版、落地页、登录页、官网、组件、仪表盘、后台页面。
- 英文：design/build/create/redesign/polish a page, landing page, login screen, website, component, dashboard, admin interface。

路由区分创建与审查：

- 创建词或明确产物 → `lily-app-builder` + `lily-ui-quality`。
- 审查、检查、视觉 QA、无障碍审计 → `lily-ui-quality` + `lily-browser-qa`。
- 创建请求同时要求预览、打开、验证或截图 → 加入 `lily-browser-qa`。

`lily-image-generation` 和 `lily-diagrams` 只处理位图和图示，不再把 UI 页面请求转发到不存在的技能。

### 评估体系

扩充 golden intent 数据，加入普通自然语言和中英文同义表达。测试直接调用真实 capability broker 并比较实际技能链，不能只验证 JSONL 结构。回归集至少包含创建、审查、纯图片、纯图示和不应触发 UI 技能的负例。

## 技能目录与注册表

### 单一来源

一方技能以 `resources/skills-catalog/<skill-id>` 为正文与 manifest 的唯一来源。强制注入技能如需位于 `resources/skills`，只保留一个规范正文，另一位置通过构建或显式引用产生，不能维护两份不同版本的 `SKILL.md`。

`lily-engineering-rules` 将消除双份正文和版本差异。所有技能分类必须来自注册表声明的受控分类，`coding` 与 `dev` 统一为一个规范值。

### 内容修订与缓存

注册表增加可确定计算的内容修订标识，例如由规范化 manifest、SKILL.md 和必要附件生成的 SHA-256 摘要。缓存比较同时检查：

- 注册表结构修订；
- 技能 ID 集合；
- 每个技能的版本；
- 每个技能的内容摘要。

对于 `bundled://local`，当前应用内置注册表在同版本时优先于旧缓存；远程注册表仍遵守签名、来源和版本策略。正文修改必须同步更新技能版本或内容摘要，CI 会阻止无摘要变化的错误发布流程。

### 来源与本地化

注册表规范化必须保留 `sourceKind`。一方技能标明 Lily 发布来源；第三方技能如保留则显示真实上游发布者和来源，不把供应商内容冒充为 Lily 原创。

补齐中文、英文和阿拉伯文名称与描述；缺失翻译按明确的 `locale → en → base` 顺序回退。RTL 元数据和长文本必须进入 UI 验证用例。

## Manifest 与权限

所有能够写文件、启动子进程、访问网络或依赖运行包的一方技能必须拥有显式 manifest。至少补齐：

- `lily-app-builder`
- `lily-code-repair`
- `lily-document-query`
- `lily-pdf-form`
- `lily-runtime-packs`
- `lily-template-fill`
- `lily-browser-qa`

权限模型表达 `filesystem: none/read/readwrite`、`subprocess`、`network` 和所需运行包。manifest 转换器只能提供保守默认值，不能把操作型技能错误降级成只读。设置页同步展示文件写入、子进程、网络和运行包提示。

权限声明只用于告知和门控，不替代底层工具权限；旧 manifest 缺字段时保持兼容并采用最小权限解释。

## 运行包与 MCP

为运行包解析增加一个统一的“有效安装目录”入口，供 spawn 环境、预检和 MCP 配置共同使用，避免三套路径推断。

Playwright MCP 注册顺序：

1. 已安装且校验通过的 `web-automation` 包。
2. 基础运行时中确实存在的 Playwright MCP。
3. 允许且可验证的系统浏览器路径。
4. 结构化 `BROWSER_RUNTIME_UNAVAILABLE` 错误。

工具 broker 不能永久绑定 unavailable handler；它应根据当前会话所需技能和运行包状态暴露真实浏览器工具。会话共享上下文需要携带有效技能能力或通过每次调用的门控上下文判断，不能因为平台上下文丢失技能 ID。

## 长时进程

`lily-app-builder` 启动开发服务器时必须使用 `lily_process_jobs`：

- 启动后返回 job ID 和实际端口；
- 通过 status/logs 检查就绪，而不是固定 sleep；
- 验证结束后按任务需要停止，或明确交给用户继续运行；
- 端口冲突、进程退出和启动超时都返回可诊断信息。

这使页面创建、浏览器 QA 和修复循环使用同一套受监督的长任务协议。

## 安全同步和孤儿清理

### 同步脚本

`sync:skills-catalog` 改为默认只生成临时输出和差异报告。正式替换需要显式标志，并依次通过：

1. 注册表 schema 校验；
2. 一方必需技能和 mandatory skills 校验；
3. ID、版本、分类、风险、权限和来源完整性校验；
4. capability gate 与意图回归测试；
5. 生成目录原子替换。

外部 catalog sources 只能更新明确允许的第三方命名空间，不能重建整个 Lily 注册表或删除一方元数据。

### 删除范围

删除以下未注册目录及相应失效 overlay、测试例外和源配置：

- `anthropics-frontend-design`
- `anthropics-web-artifacts-builder`
- `anthropics-webapp-testing`
- 5 个未注册 `superpowers-*` 目录

实际 5 个目录名在实施计划阶段从当前文件系统确定并列出，删除前由测试确认它们不在注册表、预设、路由或运行时引用中。对仍在使用的第三方技能不直接改写供应商正文；平台差异通过一方 wrapper、overlay 或 manifest 表达。

## 其他漂移修复

- `lily-document-verify` 不再硬编码仓库相对脚本路径，改用运行时解析或技能资源占位符。
- 合并语义相同的 `reliability` 和 `dev-starter` 预设，保留兼容别名但只有一个规范定义。
- 补齐 renderer 静态本地化或改为从注册表统一读取，避免新增技能在设置页缺名。
- 对 Anthropic PDF 等仍保留的供应商技能，用平台 overlay 描述 Lily 实际可用工具，不直接修改上游正文。
- 注册表 `updatedAt` 由生成流程更新，但不再作为唯一缓存失效信号。

## 测试策略

实施遵循测试先行。首先增加能够复现现状的失败测试，再做最小实现：

1. **路由测试**：覆盖中英文页面设计、创建、重设计、审查和负例。
2. **真实意图评估**：golden 数据逐条运行 capability broker，比较实际技能链。
3. **运行包预检**：UI QA 链正确要求 `web-automation`，未安装和已安装路径均验证。
4. **MCP 配置**：优先使用已安装包，基础运行时回退和不可用错误可预测。
5. **技能契约**：所有操作型技能的 manifest、权限、运行包和目录存在性一致。
6. **缓存失效**：同 ID、同 `updatedAt` 但内容摘要不同的 bundled registry 必须替换旧缓存。
7. **同步安全**：默认执行不修改正式目录；缺一方技能或元数据时拒绝替换。
8. **孤儿检查**：生产 catalog 中每个目录都被注册或明确标记为构建期资源。
9. **本地化与分类**：分类受控，三种语言按回退规则可解析。
10. **进程任务契约**：App builder 文档和能力声明要求使用 process jobs。

最后运行完整 `npm run test:unit`，并执行针对 UI 路由、运行包、MCP 和缓存的独立探针。涉及 Electron 主进程协议的变更需完整重启应用后验证。

## 实施顺序与风险控制

实施分为可独立验证的阶段：

1. 建立失败测试和注册表/目录不变量。
2. 修复技能正文、manifest、路由和意图评估。
3. 打通 Web Automation 预检、路径解析与 MCP。
4. 实现内容摘要缓存和安全同步。
5. 删除孤儿目录并清理失效引用。
6. 修复本地化、分类、预设和其他漂移。
7. 运行完整验证并检查打包产物不再包含孤儿技能。

主要风险是浏览器运行包路径变化影响已有 Web 学习能力，以及注册表缓存策略导致旧用户升级异常。两者都通过保持旧字段兼容、优先使用验证通过的新路径、保留明确回退和覆盖升级场景测试控制。任何新能力不可用时，现有通用代理能力继续可用，不因推荐技能或可选运行包失败而阻断整个对话。

## 非目标

- 不新增独立 UI 面板来操作技能；继续以自然语言和现有设置入口为主。
- 不把所有 UI 请求强制变成完整应用工程。
- 不把可选浏览器或重型运行时打进基础安装包。
- 不修改仍受上游管理的供应商技能正文。
- 不借本轮重构无关的代理会话、文档引擎或服务端业务能力。
