# 本机真实客户端验收

## 环境与范围

- 使用本机 Electron 工作台的真实 UI 发起任务，页面来自当前仓库 `src/renderer/index.html`，使用客户端现有自动模型配置；未提取或复制密钥。
- 独立测试空间：`/private/tmp/lily-live-acceptance-zNds6l`。未要求修改正式项目、发送 IM/邮件、安装依赖或部署。
- 不是模拟模型，也不是仅直接调用 CLI。未确认运行中主进程所有模块的加载版本，因此不能据此证明已发布 Mac 包包含全部修复。

## 两轮结果

1. 从空目录实现订单汇总、输入数据、7 个测试、JSON 结果和 Markdown 报告。UI 待办从 0/6 逐步推进到 6/6，最终回到空闲。独立重跑 `node test-summary.cjs`：7/7，通过，退出码 0；独立调用汇总得到 `{count:3,totalCents:1055}`，Infinity 输入抛错。
2. 验收方在测试目录把累加改为 `totalCents += cents + 1`。独立运行确认 5/7 通过、2 个失败、退出码 1。再通过真实客户端要求先复现再修复，不得改测试。模型准确找到根因；一次 edit 失败后重新读取并成功编辑，重跑后 7/7 通过。最终报告包含失败→修复→成功过程，UI 回到空闲。验收方再次独立重跑通过。

## 真实发现与后续修复

第二轮展开任务摘要显示 `delivered_unverified · 证据 9 · 风险 0 · unverified`，而独立重跑确实成功。模型实际调用的是 `node test-summary.cjs; echo "EXIT_CODE=$?"`，最终还使用了更长的复合 shell 命令。当前凭据识别器有意拒绝复合 shell，故这些命令不能构成机器验证凭据。这是保守识别的覆盖缺口，不能把复合命令最终 exit 0 直接当成内部测试通过（echo 会吞掉失败退出码）。需要后续采用结构化子进程退出证据或单独验证调用，不能简单放宽到关键词匹配。

摘要还暴露了英文内部状态码，应补用户可理解的状态展示。这次验收未修改产品实现来掩盖发现。

后续修复已实现，见 `2026-09-07-live-verification-followup.md`：严格识别真实验收使用的退出码包装并核实内部状态，补充独立最终验证调用指导，以及三语言状态标签。真实窗口重新加载后已显示中文摘要。历史未验证记录保持不变；复杂 shell、语义验收和主进程重启后的全客户端复验边界仍按该记录明确区分，不能推断全部历史任务已通过。

## 结论与边界

真实客户端已证明这一组受控任务可以完成创建、测试、交付和错误恢复，测试断言保持不变。当时发现的凭据识别和展示问题已在后续源码中修复并通过定向回归，但尚未完成最新主进程重启后的真实模型整链复验，因此不声明全部闭环。两个样本不构成复杂任务成功率基准；未做长时间断网、崩溃重启、多设备或已发布安装包验收。测试空间与会话保留用于复查，未删除用户数据。
