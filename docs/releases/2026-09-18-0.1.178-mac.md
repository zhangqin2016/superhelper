# Mac 0.1.178

## 这个版本装的是什么

起点是客户报的 Windows 卡死(0.1.176 正常、0.1.177 启动即「未响应」),查下去牵出一整条
链,最后做成了一次架构收口。**七项里有五项是删机制,不是加机制。**

### 一、客户卡死的根(以及它真正的根)

`ARTIFACT_SCHEMA_VERSION` 4→5 让每个会话的完成标记同时失效,启动时的产物回填于是重走
全部历史;而一个会话是**一整块同步工作**,完成标记又**只在整段循环跑完之后才写**——强退
一次就永远回到原点。

- 工作单位改成「一片消息」,游标每片落盘,强退最多丢一片
- 片的大小、片内时限、超大记录的隔离阈值**全部按实测成本换算**,没有一个是拍的
- 解压改为惰性(实测 200 行取压缩字节 8 ms、解压 32 ms),时钟才管得住它
- kill switch `LILY_SESSION_ENRICHMENT=0`

实测同一份真实库(1506 条,剥掉派生字段让回填真有写库工作),事件循环延迟:

| | 最大 | p95 | 中位 |
|---|---|---|---|
| 0.1.177 形状 | 1081 ms | 917 ms | 112 ms |
| 0.1.178 | 881 ms | **61 ms** | 10 ms |

**但这只是让症状可生还。真正的根是「迁移是承重件」**——显示的正确性依赖后台跑完。
关键测量定死了设计:一页 50 条,内存里重新派生 **14 ms**,写回数据库 **205 ms**。
贵的是写不是算。所以读取路径派生、只有持久化推迟,已存产物降级成**缓存**。

端到端证明:把真实库全部派生字段剥掉、后台一条不跑,打开一页得到 **24/24 条按当前
schema 显示,而库里仍是 0 条已升级**。schema 升版从此既不可能让界面错,也不可能为了
不错而必须在启动时干活。

### 二、启动门不再让大库用户干等

那道门唯一的开销是 `PRAGMA integrity_check` 逐页读完整个文件。918 MB 冷缓存实测
**3729 ms**,而门里其余所有判断加起来 **2 ms**;页面超 800 ms 就显形,所以历史大的用户
每次冷启动都在看它。

**校验没有被砍掉**——它挪出关键路径,全量扫描在窗口打开后立刻在后台跑,**每次启动的
覆盖率一字不变**。四次模拟启动:3755 ms(首次)→ 24 ms(干净退出后)→ 473 ms(模拟强
退后)→ 24 ms。标记在启动时置脏、退出时才置净,崩溃不需要被任何人捕获。
kill switch `LILY_STARTUP_FAST_ADMIT=0`。

### 三、对话显示:一个回合只能有一张卡片

现场报了三次(结束时多一张、交接留孤儿、空卡在提问下面),用户给的关键事实是「退出重启
就消失」——重复从来没进过数据,是活动渲染的产物。根因是代码里**不存在这条不变量**:

- 新增 `turn-article-mount.js` 作为回合进入列表的**唯一入口**,按身份就地替换
- 身份是 **(turnId 且 是回合卡)** —— 用户气泡为了 minimap 也带同一个 turnId
- 删掉旁路索引 `liveArticles`(DOM 之外的第二份状态,会漂移)
- 删掉 `liveTurnRenderMode` 及两个 helper(从状态算出的第二意见,会在已提交卡片尚未
  渲染时删掉活动卡,那一刻屏幕上没有任何一份答案)
- 删掉运行时补救扫描,换成**源码规则**:造回合卡又碰列表的模块必须走挂载点
- 窗口淘汰改用**回合身份**,活动卡不再被漏下变成孤卡

### 四、内部提示来源

平台自发的提示三处,只有一处贴了标记。来源在下游不可还原(引擎只运输文本),所以章盖在
**发送那一刻**,收进唯一模块 `platform-prompt.js`,并由扫源码的规则钉死。缝隙默认
kind 是 **recovery 而非 self_check**:只隐藏平台的提问,**保留模型的回答**。用户输入的
文本永不经过缝隙。

按措辞识别的两件事也拆开了:引擎自带的续跑提示是**与第三方的永久接口**(整句匹配),
我们自己的旧提示才是遗留(从前缀改为多片段签名——前缀匹配意味着用户粘贴那句话再接内容,
自己的消息就会被吞掉)。

### 五、两处静默丢弃

- `terminalTurns` / `recoveryTurns` 从进程级全局 Set 改为**每会话、有上限、随会话消亡**
- 回合结束后迟到的 `user.committed` 原本被**丢弃**(用正确顺序换掉一条消息),现在**放到
  它自己答案之前**:顺序对,且不丢

### 六、后台维护不再是哑的

产物回填接进早已存在、却只接了一个生产者的进度通道。进度以**消息**为单位(以会话为单位
时,1450 条的对话会让进度条整段不动),续跑只计剩余。真实库实测 243 个事件、单调不减、
total 1515 与真实消息数吻合。

## 验证

- 全量 **990/990**,能力门禁 **113/113**
- 真实 Electron DOM **32 项**(含用户气泡冲突、草稿优先级、孤卡淘汰、结束时重复)
- 渲染性能棘轮无变化:80 批次,0.66→1.93 ms,max 11.2 ms
- 等价性逐字节验证:整段同步跑 vs 切片+中途强退两次,557 条改写结果完全一致

## 过程中发现并修掉的自己的 bug

1. 会话排序用的 `updatedAt` 是 ISO 字符串,`Number()` 得 NaN,「最近优先」静默失效
2. 挂载点只认 `data-turn-id`,而用户气泡也带同一个 id ——**后果是助手卡整个不渲染**,
   真实 DOM 复现后修复并钉测试。该 bug 曾存在于当天早些的 Windows 包中(那些包已作废)
3. 清扫用的 `versions` 缺字段会生成 `aundefined` 后缀,把合法游标全删,**等于复活本条要
   修的 bug**;现在缺版本号就拒绝构建或删除任何键

## 限制

已补做 Apple Silicon 实际应用包的隔离启动,首页与首次使用窗口正常渲染。尚未做过客户
历史数据升级、实际自动更新后重启和物理 Intel Mac 验收。启动门、进度条、一个回合一张卡
仍需这些场景的装机验收；空白测试配置的启动通过不等于上述验收完成。
