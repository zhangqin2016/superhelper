# Windows 0.1.178

## 为什么有这个版本

客户报告:0.1.176 正常,0.1.177 启动即「智能工作台 (未响应)」,会话规模
553 / 788 / 1450 条消息。此前 Mac 发布尝试停在第一道门禁；随后 Windows 0.1.177
已于 2026-09-17 发布，见 `2026-09-17-0.1.177-windows.md`。不能据 Mac 构建时的
状态推断 Windows 未上线或客户安装包的来源。

0.1.178 只为修这一件事。

## 根因

`ARTIFACT_SCHEMA_VERSION` 在 0.1.177 里从 4 升到 5(产物相关性那次修复所需)。这个版本号
写在每个会话的「已回填」标记键里,版本一变,**所有会话的标记同时失效**,启动时的产物
回填于是重走全部历史。0.1.176 没有这次升版,所以没有这段工作。

让它从「启动慢」变成「卡死」的是两个性质:

1. **一个会话是一整块同步工作** —— 全部消息逐条解压、重新派生、写回,循环结束前主进程
   什么都答不了;
2. **完成标记只在整段循环跑完之后才写** —— 客户强退卡住的窗口,标记永远写不上,下次
   启动从头再来,所以是每次都卡。

## 修法

工作单位从「一个会话」改成「一片消息」,游标在每片之后立刻落盘 —— 强退最多丢一片。
关键量都不是写死的常数:

- 片的大小按**实测每条成本**换算(macOS 热缓存约 1 ms/条;慢机器自动缩到下限 5 条);
- **片内也按时钟收口**,因为成本是长尾的,条数挡不住尾部;
- 解压是唯一的大头(实测 200 行取压缩字节 8 ms、解压 32 ms),所以 `messageSlice` 改为
  惰性解包,时钟才真正管得住它;
- 超过 512 KB 的记录独占一个 tick;
- 会话按最近更新倒序处理。

代码在 `src/main/session-enrichment.js`,门禁 `resumable-enrichment`,回归
`scripts/test-resumable-enrichment.mjs`(9 项)。`message-store.js` 超了行数棘轮,读取面
抽到 `message-read-store.js`、envelope 格式抽到 `message-envelope.js`,棘轮从 1014
**收紧**到 913。

## 验证

同一份真实库(1506 条消息,剥掉派生字段让回填真有写库工作),心跳探针量事件循环延迟:

| | 最大 | p95 | 中位 | >100ms | >500ms |
|---|---|---|---|---|---|
| 0.1.177 形状 | 1081 ms | 917 ms | 112 ms | 12 次 | 4 次 |
| 0.1.178 | 881 ms | **80 ms** | 30 ms | 3 次 | 1 次 |

最大值只降一点,因为它是**单条记录的下限**:库里那条 13 MB 的 envelope 一条就要 1022 ms
(解压 67 + 派生 397 + 写回 558),中位数只有 5 ms,单条记录的重写无法再切分。这是公开的
已知项:一次性 0.9 秒顿卡远在 Windows 判定「未响应」之前。

等价性是证出来的:两份同样的库都剥掉派生字段,整段同步跑和「切片 + 中途强退两次」跑完,
都改写 557 条,**每条 envelope 逐字节一致**。

生产接线实跑(真实库副本 + 真实 ISO 时间戳的会话对象 + 真实 `_setTimer`):38/38 会话
完成,零残留游标。

全量测试 987/987,能力门禁 111/111。

## 顺带修掉的自己的 bug

会话排序用的 `updatedAt` 是 ISO 字符串,`Number()` 得到 NaN,NaN 比较器会让「最近优先」
静默失效 —— 看起来实现了,实际什么都没做。原来的测试用数字所以没抓到,现在按真实字段
形状钉住。

## 本版另外三项(2026-09-18 晚)

### 1. 启动门不再让大库用户每次冷启动干等

那道门是唯一的阻塞步骤,而它的开销只有一件事:`PRAGMA integrity_check` 逐页读完整个
文件。918 MB 冷缓存实测 **3729 ms**,而门里其余所有判断(文件头、schema、热日志回滚、
恢复回执、消息/会话计数)加起来 **2 ms**。页面超 800 ms 就显形,所以历史大的用户每次
冷启动都在看它。

**校验没有被砍掉** —— 砍掉校验正是丢库的方式。它只是挪出关键路径:门用「同样的判断
减去逐页扫描」放行,全量扫描在窗口打开后立刻在后台跑,**每次启动的覆盖率一字不变**。

四次模拟启动(同一份 918 MB 库):

| 启动 | 判定 | 门耗时 |
|---|---|---|
| 1(首次,无标记) | 阻塞 | 3755 ms |
| 2(上次干净退出) | 快速 | 24 ms + 后台全量校验 475 ms |
| 3(模拟强退后) | 阻塞 | 473 ms |
| 4 | 快速 | 24 ms |

标记在**启动时**置脏、`before-quit` 才置净,所以崩溃不需要被任何人捕获。仍然阻塞的
情形:上次没走到 `before-quit`、上次后台校验失败或没跑完、标记缺失/损坏/版本不符
(含首次启动与升级)。kill switch `LILY_STARTUP_FAST_ADMIT=0`。门禁 `startup-admission`。

### 2. 后台维护工作不再是哑的

产物回填接进了**早就存在、却只接了旧版迁移一个生产者**的进度通道。客户那次看到的
「未响应」,现在会是「正在整理历史记录 361/1515(可继续使用)」。进度以**消息**为单位
(以会话为单位时,那条 1450 的对话会让进度条整段不动),续跑只计剩余。真实库实测:
243 个事件、单调不减、total 1515 与真实消息数完全吻合、收尾 done===total。

### 3. 一个回合只能有一张卡片

现场现象:回答已经结束,画面里还在冒东西 —— 一个回合渲染成**三张卡片**,三张的待办
清单是同一份、停在不同进度。用户给的关键事实是**退出重启就消失**,这说明重复从来没进
过数据(重载时一条记录只生成一个 article),取本机真实库对账也确认那次提问之后只有
**一条** assistant 记录。

根因:代码里**不存在「一个 turnId 只能有一个 article」这条不变量**。活动路径按 turnId
复用,提交路径却无条件 `createElement("article")` 追加;能不能合并取决于另一处启发式
`liveTurnRenderMode` 是否恰好返回 `remove-duplicate`。新增 `turn-article-mount.js` 作为
回合进入列表的**唯一入口**,按 `data-turn-id` 就地替换。16 项真实 Electron DOM 测试
(不是 jsdom —— 这是 DOM bug,替身把 `replaceChild` 语义搞错就证明不了什么)。
门禁 `one-turn-one-article`。

全量测试 989/989,能力门禁 113/113。
