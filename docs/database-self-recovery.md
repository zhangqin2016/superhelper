# Lily 本地数据库自动修复

## 用户会看到什么

启动时，独立进程先检查会话数据库。正常数据直接进入工作台；检查较慢时显示检查进度。被占用、权限不足、磁盘读写失败和确认的损坏分别提示，不把所有异常都叫作损坏。版本来自应用自身，不再用 `0.1.0` 假装读取成功。

原生 SQLite 热日志回滚、可验证的压缩中断恢复会自动执行。确认损坏时显示独立修复页，即使普通工作台初始化或 IPC 注册失败，也可以导出诊断、退出和重启；已经启动普通服务后不允许原地替换数据库。

恢复前还会重新检查原数据库。如果它已恢复正常、仍被占用，或只是权限/磁盘问题，将拒绝用旧副本替换，而不是把“确认恢复”当成强制覆盖授权。

选择“查找可恢复副本”后显示验证通过的副本、来源、消息数和会话数。自动备份显示捕获时间；历史压缩副本和可读重建副本明确标注数据截止时间未知，不冒充“最新”。确认窗口说明较新记录可能缺失，无法计算完整损失量。取消不会替换原库。没有可验证副本时，保留原文件并提示联系支持，不提供“删除数据库试试”。

恢复成功后还需选择“继续打开工作台”。旧队列被持久隔离为结果未知，旧自动续跑申请被取消，须人工检查后重新发起；恢复副本不意味着重新授权历史写操作。首次恢复启动暂停自动任务调度，后续正常启动恢复原有调度；旧会话队列的隔离不会因此解除。新任务不受旧恢复回执残留影响。附件、工作空间及引擎数据库不是此快照的一部分，不会回滚。

## 数据与恢复协议

- `messages.db.backups/`：验证过的独立 SQLite 快照；后台首次启动约 30 秒后尝试，随后每 6 小时尝试。6 小时内已有有效快照则跳过，避免频繁重启轮换掉全部备份。最多保留 4 个有效自动快照。损坏快照、人工恢复证据不会自动删除。
- `messages.db.recovery/`：原数据库及 `-wal/-shm/-journal`、恢复候选和操作证据。先验证并写入持久恢复意图，再移动原件、发布副本。每一处可中断边界均保留可检查状态，不用空库覆盖不确定状态。
- `messages.db.recovery-intent.json`：已经确认的恢复事务。仅可恢复这一固定候选，不接受渲染器文件路径。候选内容哈希、ID、目录、原件证据必须一致，否则停止。
- `messages.db.recovery-receipt.json`：恢复完成回执。在正常启动完成前保留，防止崩溃使旧队列重新运行。队列隔离与幂等标记在 SQLite 事务内完成；回执清理失败不会再次隔离新工作。

SQLite 原生快照保留已提交 WAL 数据；不复制正在写入的主库当作有效备份。损坏原库的重写尝试只在隔离副本上运行，不声称能逐页恢复所有损坏。后台修复进程每次限时 120 秒；到时终止，进程真正退出前拒绝重叠操作。修复失败不会自动反复重启。

诊断导出只含版本、平台、修复阶段、错误分类、候选统计，不包含对话正文、密钥、附件或绝对用户路径。数据恢复全在本地，不上传客户文件。

## 验证与边界

自动测试使用临时合成数据库。真实 SQLite 测试涵盖 WAL 提交、SIGKILL 后热回滚日志、损坏/空文件、独占锁、候选被篡改、符号链接、原文件保留、恢复发布各边界故障及重启、有效自动备份轮换、时间来源、恢复后文件 inode 隔离。另有工作进程超时/退出互斥、启动顺序、回执幂等和版本降级测试。

Electron UI 测试运行实际恢复 HTML/CSS/preload/IPC，检查取消、确认、继续、三语言和窄布局。真实入口测试运行 `src/main.js` 与真实修复进程，验证损坏数据阻止普通启动、取消保持原件、确认恢复生成正确数据库与原件存档；确认对话框由测试选择响应，停止于继续进入工作台之前。

尚未验证：客户实际损坏文件、原生 Windows 文件锁/断电、物理断电、签名安装包更新和恢复后的真实模型任务。无有效历史副本的严重损坏不能保证恢复。POSIX 执行文件和目录刷盘；不声称 Windows 目录断电持久性已被本机测试证明。
