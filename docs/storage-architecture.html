会话存储架构设计

从"单 JSON 全量解析"到 SQLite + 内容寻址 Blob 仓 —— 一套不需要再推倒重来的终局设计
问题回顾：当前每个会话的全部历史（含完整 record：timeline / tools / processEvents / 内嵌附件 base64）存在一个 JSON 文件里。实测单文件已达 52.7 MB / 212 条。点击会话 → 主进程同步 JSON.parse(readFileSync(52MB)) → 事件循环阻塞数秒 → 整窗口卡死；每回合 append 又整文件重写，长会话 O(n²)。

1核心原则

① 有界读取
永远不一次性加载整个会话。任何读取都带 LIMIT，代价与历史长度无关。
② 冷热分离
列表只读"热"字段（角色/预览/排序）；重型 record 按需水合（滚入视口才取）。
③ 大体积外置
图片/文件/大工具输出不进 record，存内容寻址 Blob 仓，按需流式加载。

2三层架构

Layer 1 — SQLite better-sqlite3 · WAL

结构化数据的唯一真相源：会话元数据、消息索引、压缩后的 record、全文索引。better-sqlite3 同步预编译语句，带 LIMIT 的分页查询在 10 万行下仍是亚毫秒级——卡死从根上消失，因为再也不会读超过一页。WAL 模式提供并发读写与崩溃安全。

Layer 2 — 内容寻址 Blob 仓 filesystem · sha256

重型二进制/大文本（粘贴的图片、附件、文件 originalContent、超阈值工具结果）按 sha256 落盘到 blobs/<hash[0:2]>/<hash>，DB 里只存哈希引用。天然去重（同一张图贴两次只存一份）+ 引用计数 GC。渲染端通过自定义协议 app-blob://<hash> 流式加载，Chromium 自动缓存，内存里不再有 base64。

Layer 3 — Record 压缩 gzip / zstd

外置大附件后，单回合 record（timeline / tools 元数据 / processEvents）通常 10–50 KB，gzip 后几 KB，作为 BLOB 列存储。解析一页 = 解压 50 个几 KB 的块，毫秒级。

3数据库 Schema

-- 模式版本，迁移用
CREATE TABLE schema_meta (key TEXT PRIMARY KEY, value TEXT);

-- 会话元数据（轻量，列表/侧栏用，永不含 messages）
CREATE TABLE sessions (
  id            TEXT PRIMARY KEY,
  project_id    TEXT,
  title         TEXT,
  status        TEXT,
  agent_resume_id TEXT,
  created_at    INTEGER,
  updated_at    INTEGER,
  last_activity_at INTEGER,
  message_count INTEGER DEFAULT 0,
  archived      INTEGER DEFAULT 0
);

-- 消息：核心表。冷热字段同表，重 record 压缩进 record_blob
CREATE TABLE messages (
  session_id  TEXT NOT NULL,
  seq         INTEGER NOT NULL,          -- 会话内单调序号 = 排序键
  id          TEXT NOT NULL,             -- msg_uuid（稳定，对外引用）
  role        TEXT NOT NULL,             -- user | assistant
  turn_id     TEXT,
  created_at  INTEGER NOT NULL,
  -- 热字段：列表/搜索直接读，便宜
  preview     TEXT,                      -- content / assistantText 截断
  failed      INTEGER DEFAULT 0,
  terminal    TEXT,
  cost_usd    REAL,
  duration_ms INTEGER,
  -- 冷字段：gzip(JSON(record 去附件后))，仅水合时取
  record_blob BLOB,
  PRIMARY KEY (session_id, seq)
);
CREATE UNIQUE INDEX idx_msg_id ON messages(id);
CREATE INDEX idx_msg_page ON messages(session_id, seq DESC);

-- Blob 目录（实际字节在磁盘 blobs/ 下）
CREATE TABLE blobs (
  hash       TEXT PRIMARY KEY,           -- sha256
  bytes      INTEGER,
  mime       TEXT,
  refcount   INTEGER DEFAULT 0,
  created_at INTEGER
);

-- 消息 ↔ Blob，支持 GC 与按类型列举
CREATE TABLE message_blobs (
  message_id TEXT NOT NULL,
  hash       TEXT NOT NULL,
  role       TEXT,                      -- user_file | image | tool_result | original_content
  name       TEXT,
  ord        INTEGER,
  PRIMARY KEY (message_id, hash, role)
);

-- 全文搜索（未来需求，零额外成本预埋）
CREATE VIRTUAL TABLE messages_fts USING fts5(
  preview, content='messages', content_rowid='rowid'
);

4读写路径

打开会话（消除卡死的关键）

click → IPC getConversationPage(sessionId, limit=50) │ └─▶ SELECT seq,id,role,turn_id,preview,failed,terminal,cost_usd,duration_ms FROM messages WHERE session_id=? ORDER BY seq DESC LIMIT 50 ← 索引命中，亚毫秒 │ └─▶ 渲染端拿到 50 条骨架，立即出列表 │ └─▶ 滚入视口的 assistant turn 才水合： SELECT record_blob FROM messages WHERE id=? → gunzip → JSON record 内的图片/附件 = app-blob://<hash> ，浏览器按需流式拉取

追加一回合（消除 O(n²)）

const tx = db.transaction((record) => {
  // 1. 外置大体积字段 → blob 仓（user.files / 大 tool.result / originalContent）
  for (const big of extractHeavy(record)) {
    const hash = sha256(big.bytes);
    if (!blobExists(hash)) writeBlobFile(hash, big.bytes);
    upsertBlobRefcount(hash, +1);
    big.replaceWith({ blobRef: hash });          // record 里只留引用
  }
  // 2. 瘦身后的 record 压缩入列
  const blob = gzip(JSON.stringify(record));
  insertMsg.run({ session_id, seq: nextSeq(session_id), id, role, ..., record_blob: blob });
  bumpSession.run(session_id);             // message_count / last_activity_at
});
tx(record);   // 单事务，微秒级，无整文件重写

向上翻页（加载更早）

SELECT ... FROM messages
  WHERE session_id=? AND seq < ?       -- 上一页最小 seq
  ORDER BY seq DESC LIMIT 50;

5线程与不阻塞保证

关注点方案
查询会不会阻塞主进程？带 LIMIT 的查询命中索引，亚毫秒级——这正是 VS Code 在主进程用 better-sqlite3 的原因。卡死来自"无界解析"，有界查询不存在该问题。
极端规模 / 想彻底零阻塞把 DB 访问放进 utilityProcess（独立进程），主进程纯转发。可作为后续可选增强，接口不变。
崩溃安全WAL + 单事务写入；写一半崩溃不会损坏库，旧 JSON 的"半个文件即损坏"问题消失。
大附件加载注册 app-blob:// Electron 自定义协议，从磁盘流式返回，Chromium 缓存，懒加载，主存零 base64。

6迁移方案（兼容现有数据）

  • 一次性导入器：遍历现有 session-messages/*.json，逐条 INSERT；按数组下标赋 seq；把内嵌附件/大字段抽出落 blob 仓；建 FTS 索引。
  • 幂等 + 可恢复：以 schema_meta.migrated_files 记录已迁移文件；中断可续跑。
  • 渐进式：启动时后台迁移（带进度条），或"首次打开某会话时懒迁移该会话"，避免一次性卡顿。
  • 安全网：迁移成功后把旧 JSON 移到 session-messages.bak/，保留一个版本周期再清理。

7这套设计如何吸收未来需求（不再重构）

未来需求已预埋

导出 / 归档查询即导出；blob 按引用打包
多设备同步（远期）单调 seq + 内容寻址 blob = 天然增量同步基础
Schema 演进schema_meta.version + 迁移运行器

8渲染端配套（次要，独立可做）

存储改造后渲染窗口已被 LIMIT 50 天然限制。再补一层真·虚拟化收尾：IntersectionObserver 仅渲染视口内 turn；echarts / pdf.js / mermaid 滚入视口才初始化；离屏 turn 延迟 markdown 解析。窗口内的二次卡顿随之消失。

9落地顺序（按风险递增）

  1. 引入 DB 层：加 better-sqlite3，建 schema + 迁移运行器（不改调用方）。
  2. 双写 / 影子读：写入同时写 JSON 与 SQLite，读仍走 JSON，校验一致。
  3. 切读：getConversationPage / 翻页改走 SQLite，删 JSON 全量解析路径。← 卡死在此消失
  4. 外置 blob：附件/大字段落 blob 仓 + app-blob:// 协议。
  5. 下线 JSON：迁移完成，旧文件归档。
  6. （可选）渲染虚拟化；DB 移入 utilityProcess。
