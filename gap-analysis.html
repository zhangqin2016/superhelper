Lily Workbench vs Claude Code — 能力对标

三个视角:Agent 能力 · 工程开发 · 用户使用闭环。引擎 = vendored OpenCode;对比基准 = Claude Code (Anthropic CLI)。● 领先 · ● 持平 · ● 落后

一句话结论:引擎层(OpenCode)能力其实接近 Claude Code,甚至在多模态/学习型技能上更宽;真正的差距在我们这层(harness)对开发者工效的接线——把引擎的细粒度权限收敛成三档、没有 slash/自定义命令、没有 checkpoint/rewind、没有 IDE/headless、测试输出没结构化解析。(代码智能的诊断闭环其实引擎原生就有,见②)

定位差异(不是都该补):Claude Code 是开发者 CLI(默认信任、headless/CI、IDE);Lily 是桌面助手(GUI 优先、护栏优先、面向含非技术用户)。所以部分"落后"是有意分流。

✅ 下方 5 条优先级差距已全部实现并提交(权限 · 代码智能 · rewind · slash 命令 · headless)。

① Agent 能力 总体持平

我们领先 / 独有

  • 学习型技能(L3 结晶化):把流程自动沉淀成可复用技能并绑定工作区。Claude Code 无自动学习。
  • 多模态技能:图片/视频/语音生成、Office(LibreOffice)、视觉理解。Claude Code 仅文本/代码。
  • 预接线 MCP:邮件、浏览器(Playwright)、学习型 web 系统,开箱即用。
  • 工作区 digest + 学习约定注入提示。

引擎有、但我们没接/没开

  • 显式 lsp 导航工具(主动定义跳转/引用/hover 当工具调)experimental,Lily 未 surface。注:这只是锦上添花;真正的编辑→诊断→自纠闭环已是引擎原生且默认开(见②),不在此列。
  • plan agent 流:引擎有 plan/plan_exit 双 agent,Lily 的"Plan"只是权限只读档,非引擎的计划-审批流。
  • 后台子代理:引擎支持 async background task,Lily 未暴露给用户。
  • 引擎的细粒度 per-tool 权限被我们收敛成三档(见②)。

注:子代理(task)、read/edit/write/bash/grep/glob、web 搜索、todo、自动上下文压缩、会话恢复 — 引擎与 Claude Code 基本持平。

这块我们也有亮点

  • post-edit 验证 hook:每次写文件后跑确定性结构校验,失败同回合回灌让模型自纠(fail-open)。
  • 完成度闸门:模型声称产出文件却缺失/为空 → 自动纠正提示(一次性)。
  • diff 快照 + 一键 revert/undo,full 模式自动接受。
  • 瞬时失败(网络/超时)自动一次性重试(重生 runner + 重发)。

核心短板

  • Lily 是 OpenCode 之上的 UI+编排 harness —— LSP 诊断闭环靠引擎原生提供(已接线:node 上 PATH + 现拉 LSP server),但测试失败结构化解析、符号索引仍未集成。
  • 结果:语义错误已能编辑后即时回灌自纠;测试失败仍只回灌原始输出、无主动重试,"跑了才知道"。

③ 用户使用闭环 面向终端用户反而更强

领先(对非开发者尤其)

  • 权限模式 UI(Plan/Ask/Full)比 CLI flags 友好。
  • 交付物闭环:自动识别产出文件 + 预览/打开目录 + 图片内联。
  • 进度感:turn 时间线、活动标签、思考/工具实时展示。
  • scheduled/cron 任务:无人值守定时跑。
  • SQLite 消息存储:扛大会话不卡。
  • diff 审阅 + revert/undo 的可视化恢复。

对开发者闭环偏薄

  • 编辑→诊断→修 已由引擎原生 LSP 回灌打通(见②);仍缺的是 测试 这一环的结构化解析与自动重试。
  • 权限信任工效差:无"src 自动、tests 询问"这种 per-path 自动。
  • 无会话级 rewind,探索式开发回退成本高。
  • 无 slash/自定义命令,重复性开发流程要每次手敲。
