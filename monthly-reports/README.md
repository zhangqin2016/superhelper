# 月报总结（monthly-reports）

本目录存放**项目工程月报**：每月月底生成一份当月简报，覆盖当月工程实施的主要内容，
以及工程侧和团队侧的重要待办事项。

## 目录约定

| 文件 | 说明 |
|------|------|
| `README.md` | 本文件：制度、流程、写作规范 |
| `TEMPLATE.md` | 月报模板；生成器按它铺骨架 |
| `YYYY-MM.md` | 某个月的月报，例如 `2026-08.md`。一个月一份，不拆分 |

命名只用 `YYYY-MM.md`，不加后缀、不加中文名，方便脚本按月定位。

## 生成流程

**时间**：每月最后一个工作日（月底）。当月未结束时不定稿，可以先生成骨架边写边补。

```bash
npm run report:monthly            # 生成/刷新当月（按今天所在月份）
npm run report:monthly 2026-08    # 生成/刷新指定月份
npm run report:monthly -- --print # 只打印数据附录，不落盘
```

脚本做两件事：

1. 首次运行时用 `TEMPLATE.md` 铺出骨架文件；
2. 每次运行都从 git 重新统计当月数据，覆盖写入文件末尾
   `<!-- AUTO:BEGIN -->` 与 `<!-- AUTO:END -->` 之间的**数据附录**。

这两个标记之外的正文**永远不会被脚本改写**——重复运行是安全的，可以随时刷新数据附录。
数据附录属于机器生成，不要手工编辑；要改就改脚本。

## 写作规范

1. **写给不看代码的人。** 月报的读者是要做判断的人，不是提交历史的读者。
   同一件事先说它对客户意味着什么，再说我们做了什么，技术名词点到为止。
2. **不要列提交。** 附录里已经有机器统计，正文要的是判断：这个月最贵的问题是哪个、
   根因是什么、防住了没有。凑不出判断的部分宁可不写。
3. **每条结论都要有出处。** 提交、测试、能力清单、验收文档、线上版本号，任选其一能对上。
   写不出出处的，说明还没做完，应该挪到待办。
4. **不粉饰。** 没验证的不写成已完成，跳过的步骤明写跳过，测试因为环境跑不起来就如实说。
5. **工作量写成价值。** 投入数字放在支撑位置，紧跟一句它说明了什么——
   是在造新，还是在还质量的债。数字本身不是成绩。
6. **控制长度。** 一份月报三分钟能读完。细节留在 `docs/` 的设计与验收文档里，月报只给索引。

## 数据来源

- 提交、发版、改动规模、新增测试：git（由生成器统计）
- 待办与阻塞：`memory/MEMORY.md` 各条目的"pending / 待"部分、`HANDOFF.md`、
  `CAPABILITY-GATE.md`、`docs/` 下的 `*-plan.md` 与验收文档中未闭环的项
- 线上状态：`docs/` 下当月的验收/发布记录
