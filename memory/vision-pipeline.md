**By default the main LLM is TEXT-ONLY (cannot see images).** So an attached screenshot is NOT sent as an image block to the main engine. Instead a **separate Qwen vision model (DashScope / Aliyun Bailian)** recognizes the image into text, which is appended to the user's message; the user's typed text carries the *intent*, the vision text carries the *image content*, and the main engine analyzes from that context.

**EXCEPTION — native-vision models (added 2026-06-14):** a model preset can declare `capabilities.vision: true` (server-delivered in `effectiveConfig.models.presets[]`, or in the packaged catalog; default false). When the *active* preset has it, `runVisionPreflight` is given `nativeVision: true` (via `model-presets.activePresetSupportsVision()`, a try/catch-guarded probe) and **bypasses Qwen entirely, keeping the image files** so `agent-session.buildUserMessagePayload` (user-message.js) sends them as real base64 image blocks to the multimodal engine. Admin toggles it per-preset in `config-profile-form.js` ("模型原生支持图片识别"). So: only enable for models that genuinely accept image blocks; for text-only models leave it off → Qwen bridge.

Flow: `turn-orchestrator._startTurn` → `send-preflight.runVisionPreflight(text, files, {emitNotice})` → `vision-translator.translateImages` (config from settings.json env: `VISION_API_KEY`/`DASHSCOPE_API_KEY`, `VISION_MODEL` e.g. `qwen-vl-plus`, `DASHSCOPE_BASE_URL`). On success the image is replaced by `[Image recognition result: …]` text and pruned from outbound files.

**Bug fixed 2026-06-13** (symptom: attached a screenshot, assistant analyzed the workspace directory instead): `translateImages` returns `{ok:false, reason:"API_FAILED"}` on a `Vision API timeout`. The default `VISION_TIMEOUT_MS` was **15s — too short** for qwen-vl on a full screenshot (succeeds at ~60s). On that failure, send-preflight **silently dropped the image and sent bare text** to the text-only engine → it answered blind. Fixes: (1) default timeout 15s→60s (`vision-translator.js`); (2) send-preflight now **fails loud (`VISION_FAILED`)** when vision is *configured but fails*, so the user retries — but `NO_KEY` (vision not configured) + text still degrades to text-only (deliberate, pinned by `test-image-send-flow`); (3) guarded `bundledResourceCandidates` `path.join(process.resourcesPath,…)` against undefined. Quick user workaround without an app rebuild: set `"VISION_TIMEOUT_MS":"60000"` in `<userData>/lily-config/settings.json` env.

**Server-side vision/search proxy (added 2026-06-14):** vision recognition no longer needs the key on the client. `server/src/services/media-gateway.js` exposes `POST /llm/vision/chat/completions` (forwards to DashScope compatible-mode with the server's `DASHSCOPE_API_KEY`) and `POST /llm/search` (forwards to Aliyun IQS with the server's IQS key). `withGatewayRuntimeConfig` (client-config.js) injects `DASHSCOPE_BASE_URL=<base>/llm/vision` + `VISION_API_KEY=<gateway token>` (and `WEBSEARCH_IQS_API_URL`/`WEBSEARCH_IQS_API_KEY` for search) into the delivered `runtime.env` whenever the server holds the key — so `vision-translator` (reads `DASHSCOPE_BASE_URL`/`VISION_API_KEY`, token wins over local `DASHSCOPE_API_KEY`) and `websearch.cjs` (reads `WEBSEARCH_IQS_API_URL`) route through the server with a short-lived token, no client rebuild. Tokens are provider-scoped ("vision"/"search"). Vision is live (server has the DashScope key); search activates when an IQS key is added to server env. NOTE: the **raw** `DASHSCOPE_API_KEY` is still delivered via `runtimeEnvFromServerConfig` for image-gen/video/TTS skills (not yet proxied) — those still use a client-delivered key.

Note `translateImages` returns `null` only when there are no image files; `{ok:false}` only on NO_KEY or ALL images failing (partial success returns ok:true with `[Image: name]` placeholders).
