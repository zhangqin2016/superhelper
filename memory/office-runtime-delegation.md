The user's standing rule for document handling: **never hand-roll it — delegate to the bundled best-in-class libraries.** "我们的代码 不再自己做这种事情 能用顶级的就用顶级的."

**Why:** `document-translator.js` originally hand-parsed Office XML in JS with regex (`stripXmlTags`, reading `word/document.xml` / `xl/sharedStrings.xml` directly). This flattened all table/sheet structure — the xlsx path just dumped shared strings as a flat list, useless for real spreadsheets — and broke on real-world files.

**How to apply:** `resources/runtime/requirements-runtime.txt` is the source of truth for the light base Python runtime; `bundles/<platform>/runtime` is generated build output, not source. Default Mac/Windows installers are slim and explicitly exclude generated runtime/runtime-pack directories, so optional/heavy capabilities must come from verified runtime-pack artifacts. Never hand-`pip install` into a packaged venv as a fix — declare direct imports in `requirements-runtime.txt`, rebuild the base runtime when producing that distribution, or publish a runtime pack through the verified artifact pipeline.

Main-process document work delegates via `resolveVenvPython()` (runtime-python.js) running `resources/runtime-scripts/extract_document.py` → `{ok, text}`, tables as Markdown. Routing by format (deliberate — top-tier where it matters, fast where it's already optimal):
- **PDF → pdfplumber text layer; scanned pages → pypdfium2 render + RapidOCR.** `extract_pdf` reads each page's text layer (digital PDFs, the ~90% case: ~41MB / 0.06s). Only pages with no text layer (scans) fall through to render at scale=2 + RapidOCR (onnxruntime). OCR import is lazy/cached (`_get_ocr`) so digital PDFs and Office files never load onnxruntime. RapidOCR ships its 3 onnx models (~16MB) in the wheel → offline OCR, no pre-download.
- **Standalone images (.png etc.) → vision path, NOT this extractor.** `isExtractableDocumentFile` rejects `file.isImage`; images go to `vision-translator` (multimodal model). The `extract_image` branch in the script is only reachable if called directly. The reachable OCR case via `extractDocuments` is an image-only/scanned PDF.
- **docx/xlsx/pptx → fast native libs** (python-docx in-order walk, openpyxl, python-pptx). Already top-tier.

**Torch/Docling was tried and then deliberately removed (2026-06-13).** The product is "给普通人用的智能工作台" (a consumer smart workbench). Docling+torch raised the bundle 1.3G→2.8G, PDF peak RAM to ~1.08G, and cold start to ~43s — "like it froze" on an ordinary 8GB Intel laptop. The user chose **彻底轻量** (fully lightweight): remove torch/Docling, keep pypdfium2+pdfplumber+RapidOCR. Net: runtime 2.8G→1.4G, venv→559M, digital PDF instant. PyMuPDF avoided too — AGPL risk for a commercial product; pypdfium2 is Apache. Honest caveat: the OCR (scanned) path still peaks ~1.3GB RSS from onnxruntime's memory arena, but it's transient and only the minority scanned case.

**Three-tier document capability (decided 2026-06-13).** Standard tier = the light base (already ~80% of a proposed "standard" lib list, mostly Python): MarkItDown (bundled), python-docx/openpyxl/pandas (Office read), RapidOCR (= PaddleOCR's PP-OCRv4 models on onnxruntime, NOT PaddlePaddle — same quality, no torch), docxtpl + pypdf + LibreOffice (already bundled, lo=25.8.7). Rejected as redundant/heavy when the user proposed them: SheetJS/ExcelJS/Mammoth (Python already covers), PaddleOCR proper (re-adds torch-class weight). Pro/expert engines (Docling/MinerU/Marker) are NOT bundled — they're **runtime packs** via `src/main/runtime-packs.js`: `PACKS` registry + `installPack`/`uninstallPack`/`verifyPack`/`listPacks`. **Install is artifact-first, for China reachability (decided 2026-06-13 — PyPI is slow/blocked there):** `installPack` asks the server (`service-client.runtimePackArtifact(pack, platform)` → `GET /api/runtime-packs/artifact`) for a `{url, sha256, version}`; URL points at a Qiniu CDN object, configurable server-side. App downloads (streamed, https-only except localhost) → verifies sha256 → extracts tar.gz into `userData/runtime-packs/<id>/` (NOT the venv — it's read-only once packaged; this is why the old uv-into-venv path only works in dev) → that dir goes on PYTHONPATH so `extract_document.py::_try_pro_pdf` lazily imports docling and upgrades. Uninstall = delete the dir. `uv pip install` remains a dev/offline fallback (`installPackRequirements`, source:"pip"). Artifact = `uv pip install --target` output tarred + uploaded. Build script: `scripts/build-runtime-pack.mjs --pack <id> [--platform]` → installs to a stage dir, verifies the probe, packs tar.gz, derives version from the main package's dist-info, prints `{packId, platform, version, sha256, sizeBytes}` + the `POST /api/admin/runtime-packs` body. Same-platform only (torch wheels are platform-specific — run on each target OS). Pack catalog data lives in `src/main/runtime-pack-specs.js` (pure, no electron) shared by `runtime-packs.js` + the build script. Real pro-pdf artifact built & verified on darwin-arm64 before the rename: docling 2.102.1 + torch 2.12.0, **233MB download / 909MB installed** (NOT the ≈2.5GB I first guessed). After the runtime-pack rename, register that artifact under `runtime_packs` before releasing/deploying the new server. `dist/runtime-packs/` is gitignored. Server side mirrors `releases`: migration `009_runtime_packs.sql` (table `runtime_packs`, unique pack_id+platform+version), public route in `public/catalog.js`, admin CRUD `admin/runtime-packs.js`. Gotcha: `serviceFetch` returns `{ok, json}` — read the artifact under `.json.artifact`. IPC: `runtimepacks:list/verify/install/uninstall` (+ `runtimepacks:progress`). Admin UI exists at `/admin/runtime-packs`; agent install uses skill `lily-runtime-packs` + `manage_runtime_pack.py`. `test-runtime-packs.mjs` covers the full artifact flow offline via a localhost http server + stub tarball; server smoke/integration need Postgres.

**Task-aware readiness pipeline (implemented 2026-07-11).** The source-of-truth flow is `capability-readiness plan → runtime-pack coordinator → resumable download/checksum/staging health → idle runner + MCP refresh → exactly one turn dispatch → evidence/verification`. Skill presets never install runtime packs; they remain instant and dependency-lazy. Only hard requirements inferred from the current task may prepare before dispatch; enhancements stay optional. Preparation is deduplicated, concurrency-bounded, visible in chat, and fails open once to the existing strong baseline with an explicit evidence limitation. Production artifact coverage is a release responsibility governed by `resources/runtime/runtime-pack-lock.json` and strict release preflight—not something users should repair manually. Missing Intel macOS or Windows artifacts must block release until built and probed on the target host; hashes are never copied across platforms.

**document_verify (visual QA loop):** `resources/runtime-scripts/render_document.py` renders any doc to per-page PNGs (Office→LibreOffice→PDF→pypdfium2; PDF rasterized direct) — the deterministic "eyes"; the model does the layout judgment (Rule 5). Skill `lily-document-verify`. **PDF form fill:** skill `lily-pdf-form` + `fill_pdf_form.py` (pypdf AcroForm `update_page_form_field_values`, NeedAppearances for CJK). For *layout* PDFs (contracts/certs) use template-fill→LibreOffice, NOT a draw-by-coordinates lib — pdfme (Node) was rejected: second toolchain for capability pypdf+docxtpl+LibreOffice already cover. Three first-party skills now in catalog (143 total): `lily-template-fill`, `lily-pdf-form` (both in `office-starter`, now 7), `lily-document-verify` (discoverable, not auto-bundled).

Office generation for the agent goes through the `anthropics-docx/xlsx/pptx/pdf` skills (also Python). Do NOT add Node-side Office libs (docxtemplater/ExcelJS/PptxGenJS) — second toolchain; the stack is Python. Do NOT edit the vendored `anthropics-*` skills (LICENSE: Proprietary) — build first-party `lily-*` skills instead.

**Template fill — done (2026-06-13), as a first-party agent skill, not a main-process feature.** The user chose conversational trigger: the model maps NL/uploaded data → `{placeholder: value}` (the judgment part), code does the deterministic render (Rule 5). Skill `lily-template-fill` (`resources/skills-catalog/lily-template-fill/`): `SKILL.md` + `scripts/fill_template.py` (docxtpl). Script has two subcommands — `inspect <tpl>` → declared `{{ }}`/`{%p %}` variables; `fill <tpl> <data.json> <out>` → renders + returns `missing` (declared-but-unprovided, surfaced loudly, never silent blanks). `docxtpl>=0.16,<1` added to requirements (light: +docxtpl/jinja2/markupsafe ≈1MB, rides existing python-docx). Wiring for a bundled first-party skill to be discoverable + offline-installable: (1) catalog dir with `SKILL.md`, (2) entry in `resources/skills-registry/registry.json`, (3) zh-CN entry in `skill-localization/zh-CN.json`, (4) optional preset membership in `skill-presets.js` (added to `office-starter`). Skills are filesystem-discovered (`skill-bundled-catalog.js` resolves `<id>/SKILL.md`); registry.json is the listing. Test: `scripts/test-template-fill.mjs` (auto-discovered by run-all-tests). `test-skill-presets.mjs` hardcodes office-starter counts — bump them when changing that preset.
